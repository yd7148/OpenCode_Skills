# 判讀指南 — 「單一網站連不上」的歸因方法

本文件處理一類 `network-port-check` 主流程**不會**自動涵蓋的問題：

> 整體網路正常（大部分網站都通），但**某一個特定網站／雲端服務連不上**。

這時不能直接套用「白名單 ACL 防火牆」的結論。
本文件提供一套**可重現的歸因流程**，用來判定責任到底在本機、ISP，還是服務端。

---

## 零、先分清兩種「連不上」

| 類型 | 徵狀 | 適用章節 |
|------|------|----------|
| **A. 廣泛性** | 大量網站都連不上 | 主 SKILL 的 port 矩陣流程 |
| **B. 單點性** | 只有 1～2 個網站連不上 | **本文（單點歸因）** |

> ⚠️ 常見誤判：看到單一網站失敗就說「被防火牆擋」。
> 這幾乎總是錯的——防火牆不會只挑某個網域擋。

---

## 一、五層歸因流程（依序執行）

遇到「某網站連不上」時，**由上而下**跑這五層。
前一層成立就不用往下，**不要跳層下結論**。

```
第 1 層  DNS 解析        失敗 → 網域可能已廢棄，不是網路問題
   ↓
第 2  層  TCP 443        失敗 → 進入第 3 層（本文件重點）
   ↓
第 3  層  分組對照        同一組織的其他站台通嗎？→ 決定責任歸屬
   ↓
第 4  層  GeoIP / ASN     解析到的 IP 在哪個國家、哪個營運商？
   ↓
第 5  層  本機排除        防火牆 / Proxy / DNS 污染
```

---

## 二、第 3 層：分組對照（本流程的核心）

### 為什麼這層最重要

只有一個網站失敗時，**最有價值的證據不是那個失敗的網站，而是它的同業對照組**。

實測範例（夸克雲盤）：

```
❌ pan.quark.cn        203.119.169.79   443 不通
✅ www.quark.cn         47.246.165.152  443 通     ← 同一間公司！
✅ www.aliyun.com       47.88.128.4     443 通     ← 同一個 parent
✅ www.taobao.com      155.102.184.210  443 通     ← 同一個 parent
```

**同一台電腦、同一條網路、同一家公司，官網通而雲盤不通。**
這在邏輯上直接排除了「本機防火牆」「ISP 封鎖」——
因為這兩者都不會區分同一家公司的不同站台。

### 對照組怎麼選（依序）

1. **同組織不同產品**：`pan.quark.cn` → `www.quark.cn`（最佳）
2. **同 parent 集團**：`www.quark.cn` → `www.aliyun.com`
3. **同 IP 段不同主機**：`203.119.169.79` → 該段其他主機
4. **完全無關的知名站**（最弱）：`drive.google.com`

> 對照組一定要**實測**，不能憑印象。
> 同一台機器上 A 通 B 不通是常態。

### 對照結果怎麼判讀

| 對照組結果 | 結論 |
|-----------|------|
| 對照組**全通**，目標不通 | **服務端問題**（進入第 4 層） |
| 對照組**全不通** | 本機或網路問題（進入第 5 層） |
| 對照組**部分通** | 依「什麼共通點」再分（通常是 IP 段／地理位置） |

---

## 三、第 4 層：GeoIP / ASN 交叉驗證

當對照組全通、目標不通時，下一步是**看 IP 到底長什麼樣**。

### 查 GeoIP

```powershell
curl.exe -sS "https://ipinfo.io/<IP>/json"
```

回傳欄位中最重要的三項：`country` / `region` / `org`（含 ASN）。

### 實測對照表

| IP | GeoIP | ASN | 連線 |
|----|-------|-----|------|
| `203.119.169.79` | **CN / Hebei** | AS37963 | ❌ |
| `203.119.175.186` | **CN / Hebei** | AS37963 | ❌ |
| `203.119.204.199` | **CN / Hebei** | AS37963 | ❌ |
| `47.246.165.152` | SG / Singapore | AS45102 | ✅ |
| `47.246.136.220` | US / Virginia | AS45102 | ✅ |

**100% 對應：CN/AS37963 全擋，海外/AS45102 全通。**

### 這個模式代表什麼

服務商的 **geo-routing 把台灣流量派到中國大陸機房**，
而該機房防火牆**不對境外 IP 迴應**。

典型徵兆：
- 同一組 IP 在**多次查詢中輪替**（DNS round-robin），但每個都不通
- 換成海外節點的 IP 就通
- ICMP 與 TCP **同時**被丟包（不是 port 層過濾）

> **排除「單一 IP 故障」的方法**：多查幾次。
> 若每次拿到不同 IP、但規則完全一致（CN 全掛 / 海外全通），
> 就不可能是那個 IP 壞掉，而是整段有問題。

### DNS 交叉驗證（確認不是 DNS 污染）

```powershell
curl.exe -sS "https://dns.google/resolve?name=<主機>&type=A"
curl.exe -sS -H "accept: application/dns-json" "https://cloudflare-dns.com/dns-query?name=<主機>&type=A"
```

若 Google 與 Cloudflare **回傳相同的境外 IP**，則 DNS 沒有被污染，
問題出在該 IP 本身不可達。

## 四、第 5 層：排除本機因素

```powershell
# 1. 出站封鎖規則
Get-NetFirewallRule -Direction Outbound -Enabled True |
  Where-Object { $_.Action -eq 'Block' }

# 2. 防火牆預設出站動作（NotConfigured = Allow）
Get-NetFirewallProfile | Select Name, DefaultOutboundAction

# 3. 系統 Proxy
netsh winhttp show proxy
Get-ItemProperty 'HKCU:\...\Internet Settings' | Select ProxyEnable, ProxyServer

# 4. ICMP vs TCP 分離測試
Test-Connection <IP> -Count 3      # ICMP
Test-NetConnection <IP> -Port 443  # TCP
```

### 判讀

| 觀察 | 意義 |
|------|------|
| 無任何 Outbound Block 規則 + 預設 Allow | 本機防火牆無罪 |
| ICMP 通但 TCP 不通 | 目的地過濾特定 port |
| **ICMP 與 TCP 都不通** | 目的地完全不對你的 IP 迴應（服務端問題） |

---

## 五、責任歸屬速查

| 現象組合 | 責任歸屬 |
|---------|---------|
| 對照組全通 + 目標 IP 在境外段卻不通 | 服務端該區段故障 |
| 對照組全通 + 目標 IP 在中國/受限地區段 | **服務端 geo-routing 問題** |
| 對照組全通 + 目標 ICMP/TCP 皆無回應 | 服務端封鎖你的來源 IP |
| 對照組全不通 | 本機或網路（進第 5 層） |
| 目標站 4xx/5xx | **不是封鎖**，伺服器有回應（主 SKILL 已涵蓋） |

---

## 六、給使用者的輸出格式

診斷完畢，報告要回答三個問題，順序不能顛倒：

```
1. 誰的問題？      → 具體到組織（例：Alibaba 夸克，不是「網路有問題」）
2. 為什麼？        → 用對照組證明，排除本機與 ISP
3. 那我怎麼辦？    → 可立即執行的替代方案
```

### 實測輸出範例

```markdown
## 結論

不是你的電腦壞了，也不是 HiNet 擋你。
這是 Alibaba 自己把台灣的流量導到中國大陸的機房，而那批機房的防火牆不對境外開放。
責任歸屬：Alibaba 夸克團隊（境外服務未提供台灣節點）。

## 關鍵證據

| | 網段 | GeoIP | 結果 |
|---|---|---|---|
| 夸克雲盤 | AS37963 | CN / Hebei | ❌ 全掛 |
| 夸克官網 | AS45102 | SG / Singapore | ✅ 通 |

## 行動建議
1. 改用行動網路下載後傳輸
2. 請對方改用其他雲端
3. 向服務商申訴（附對照表）
```

### 務必提醒的第二層障礙

> 即使網路通了，服務本身仍可能下載不了。
> 實測範例：夸克分享連結需**登入 Cookie** 才能完整下載，
> 且第三方 CORS relay（allorigins 520／codetabs 522／jina 403）全被反爬蟲擋下。

**先講清楚這點，可以避免使用者修好網路後才發現還是不行。**

## 七、附帶教訓

### 1. 不要過早承諾能下載

使用者說「幫我下載 X」時，先做一次可達性確認再動手。
本次案例中，目標從一開始就完全不可達，任何下載嘗試都只是浪費時間。

### 2. 本地 proxy 埠號要辨識清楚

瀏覽器報 `ERR_TUNNEL_CONNECTION_FAILED` 時，
先確認該 proxy 是**環境提供**還是**工具自身的 tunnel**。
本次 `127.0.0.1:9125` 屬於後者，**不能**拿來當繞道方案。
`Get-NetTCPConnection -State Listen` 查不到監聽者 → 不是本機 proxy。

### 3. 瀏覽器驗證是最終確認

命令行測完再用瀏覽器開一次。若瀏覽器也失敗，
可確認不是工具的語意問題，而是真的連不上。
